# Provenance of every reported value

This file maps each number printed in the manuscript (`paper/main.tex`, `paper/supplement.tex`,
`paper/tables/*.tex`) to the result file it is read from, the column and row filter, the script
that wrote the file, the job and exact command that ran it, the code version stamped in the
file's provenance record, and a one-line description of how it is computed.

It is generated by `docs/provenance_check.py`, which reads `results/` (it never writes there),
recomputes every mapped value, formats it at the printed precision and compares it with the
printed string. Sections 3–5 below are written by that script; this header is
`docs/provenance_header.md`. To rebuild after a rerun or a text change:

```bash
python3 docs/provenance_check.py            # check only; exit 1 on any mismatch
python3 docs/provenance_check.py --write    # check and rewrite docs/PROVENANCE.md
```

Definitions of every column name used below are in [`METHODS_NOTES.md`](METHODS_NOTES.md).

## 1. How to read the map

**Columns of section 4.** *Printed*: the value as it appears in the PDF (`<=` marks a bound,
`a -- b` a range). *Source*: `file [row filter] column` under `results/`. A filter such as
`[tariff=inforce, arm=TUNED]` selects the single summary row; a file name containing `{c}` or
`<c>` is per city. *How*: the computation. *Check*: `OK` when the file value, formatted at the
printed precision, equals the printed string.

**Rounding rule.** Every cell is the unrounded file value rounded once (Python `format`, i.e.
nearest, ties to even on the stored binary value) to the printed number of decimals: savings and on-command
changes to one decimal (points or %), temperature offsets to 0.001 K, p-values to 0.001.
Differences between two arms (Δs in `tab:stats`, the MPC margin over TUNED, F4) are computed
from the **unrounded** values and then rounded to one decimal, so a printed difference can
differ by 0.1 from the difference of two printed cells (e.g. Riyadh F2: 18.2638 − 12.5260 =
5.74 → 5.7, while 18.3 − 12.5 = 5.8). Bounds B\*, B_a and the ruled bound are rounded
**outward** (up) to 0.1 point (`bound_v2.up01`), so they remain valid bounds after rounding.
Money (SAR per room per season) is rounded to whole riyals.

**The protocol behind every saving (RULING_round4 §2; code: `final_tables.py`, `t1_v2.evaluate`).**

* *Windows.* Thirteen 168-h windows starting every 14 days from day index 121; six tuning
  windows select parameters (Rule A), seven held-out windows (day indices 121, 149, …, 289)
  are scored (Rule C). Every number in the main tables is a held-out number.
* *Comfort (Rule B, §2.1).* Occupied band [22, 24] °C. Comfort is scored on the post-step state.
  An arm is admissible on a window only with zero occupied over-temperature (`deg_h_over`) and
  zero cooling-caused under-temperature (`deg_h_cmd_under`, the cold rule); free-float drift
  below the band (`deg_h_ff_under`) is allowed and reported. Matching uses the **clipped**
  occupied mean T̃ (temperatures below 22 °C count as 22 °C, so cold excursions buy no warm
  credit).
* *Selection (Rule A4, §2.2).* Among admissible candidates, the one with the lowest tuning cost
  ratio whose pooled clipped mean over the tuning windows is within 0.03 K of THERM's
  (`fit_status = pooled_0.03`); if none exists, within 0.10 K (`pooled_0.10`, the single
  fallback, marked ᵇ in the tables); otherwise no row is written (`none`, refused by
  `rbrl_io`). `oracle` marks the clairvoyant schedule (multiplier bisected per held-out window),
  `fixed` a parameter set by the caller rather than selected (λ = X·λ\*, the no-rules PPO with a
  fixed cap, setpoint shifts), `reference` THERM itself in the multi-zone files.
* *Comfort equalisation and the saving (Rule C, §2.3, §13).* On each held-out window THERM is
  re-run shifted by δ ∈ [−0.4, 0.4] K (step 0.002 K); the shift whose clipped mean equals the
  arm's is found on that curve, taking the **cheapest** crossing when there are several
  (conservative; `s_eq_maxJ` reports the dearest). The arm's saving is
  s = 100 · (1 − Σ_w J_arm,w / Σ_w J_THERM(δ_w),w) over the seven held-out windows
  (`s_pooled_eq`). On-commands and electricity are compared with the same equalised THERM
  (`start_sav_eq`, `energy_sav_eq`). A comparator outside the ±0.4 K bracket is clipped and
  flagged (`eq_clipped`, `n_eq_clipped`).
* *Comfort-offset caveat.* A residual pooled offset `dT_pooled` of 0.01 K is worth about
  1.3 points of saving; rows with |ΔT̃| above about 0.02 K carry the caveat in the text.
* *Bracket.* The clairvoyant schedule (CLV) and the relaxed Lagrangian dual bound B\* both use
  the O4 terminal value V_N (energy at rated COP plus c_sw per 1 K of end-of-week temperature
  above the start). Causal arms use the simulator's energy-only terminal; `T17v3_Ba` rescored
  every arm onto V_N and evaluates the bound B_a at each arm's own pooled mean.
* *Three layers (§24).* (1) on-commands avoided, `start_sav_eq`; (2) electricity, `energy_sav_eq`;
  (3) money per room per cooling season, 184 · [c_sw (f̄_eq − f̄_arm) + 0.18 (Ē_eq − Ē_arm)]
  with f̄ the mean on-commands per day and Ē the mean kWh per day over the held-out windows, at
  c_sw = 0.025 / 0.114 SAR and, in brackets, the 0.15 SAR computational reference. This table
  is not written by a code-of-record script; `docs/provenance_check.py` recomputes every cell
  from the per-window files.
* *Statistics (§2.4).* Per-window differences of the equalised savings, n = 7; Hodges–Lehmann
  estimate with its exact 95.3 % interval, exact Wilcoxon signed-rank and sign tests, Holm within
  each three-city family; a pooled difference below 3 points is "not resolved" whatever the test.

The generators write their own provenance header (input file shas) into each `.tex` they
produce; `python3 verify_numbers.py` (class E) checks that every generated table was made from
the current bytes of its inputs. The manuscript editor narrowed the layout of the inlined tables
and of `tab_stats.tex` and added the ΔT̃ₐ − ΔT̃_b column and the fallback marks to the latter (its
header lines say so); the numbers were not retyped, and the check below compares every cell with
the result files directly. `tab:layers` and the text values are verified only by the check below.

Before running any generator, follow the README section *Reproducing the results* (weather files,
the `code/results → ../results` link and the original-path link).
